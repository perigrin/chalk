## Executive Summary

The branch meets its loader goal: every op B::SoN emits for the pvm corpus now loads. But three ways of reading or writing fields in class methods now produce wrong answers or modules lli rejects. The corpus census does not exercise them, so it still shows 0 DIFFERS and 0 LLI_FAIL. Two of the three are regressions from 61dabdf4, the commit that freezes field reads; the third comes from 9661206e, which lets class programs load at all. Confidence is high: the verifier reproduced every Critical and Important finding at HEAD and checked it against base.

## Critical Issues

### [C1] A cached field read that was never frozen is reused in blocks it doesn't dominate
- **File:** `lib/Chalk/Target/LLVM/Context.pm:1580-1584`
- **Bug:** The new early return in `lower_value` serves `{cache}{id}` for any FieldAccess that has a memory input. But `_freeze_memory_reads` runs only at MemStart and after an Assign or shift/pop. `_lower_field_access_in_method` writes the cache on every lowering. So a read at a method-call or Phi memory version is lowered at its first use and then reused in sibling arms.
- **Impact:** `method bump { $n = $n + 1 } method m ($c) { $self->bump; if ($c > 1) { print $n } else { print $n, "!" } }` makes lli fail with "Instruction does not dominate all uses!" (LLI_FAIL). At 9661206e it printed the correct `2!|2|`.
- **Suggested fix:** Record frozen ids in a set inside `_freeze_memory_reads`, and take the cache hit only for ids in that set. Any other read is re-lowered at its use, as it was before.
- **Confidence:** High
- **Found by:** Concurrency & State, Error Handling, Contract & Integration, Logic & Correctness (`claude-opus-5-5[1m]`)

### [C2] A field read after `$n += …` returns the value from before the `+=`
- **File:** `lib/Chalk/Target/LLVM/Context.pm:5324-5337`
- **Bug:** B::SoN lowers a field `+=` to `Assign(FieldAccess, Add(FieldAccess, …))`. The read after it is `FieldAccess(inputs=[MemStart])`, because the memory version does not move past the store. HEAD now freezes that read at MemStart, so it returns the stale value.
- **Impact:**
  - `field $n = 1; method m ($c) { $n += $c; … print $n … }`: perl prints `2!` / `3`. HEAD prints `1!` / `1` (DIFFERS). At 9661206e the output was correct.
  - `$n += 1; my $old = $n; $n = 5; "$old$n"`: perl prints `25`, HEAD prints `15`.
- **Suggested fix:**
  - **chalk:** refuse with a GAP when a field Assign produces no memory version that a later read of the same field consumes, but an earlier-version read of that field is used after the store.
  - **perl5-son:** separately, report that B::SoN does not thread memory through a field `+=`. `$n = $n + 1` threads correctly.
- **Confidence:** High
- **Found by:** Error Handling (`claude-opus-5-5[1m]`)

### [C3] Class programs that the PackageMark no-op now lets load can give wrong answers
- **File:** `lib/Chalk/Target/LLVM/Context.pm:5106-5115`
- **Bug:** Until 9661206e, any `class` program failed to load ("Unknown data node operation: PackageMark"). Now these programs reach method lowering, and field state behind a branch is not merged:
  - `if ($c) { $n = 3 } return $n`: perl prints `31`, HEAD prints `11`.
  - A store under one `if` followed by reads in a second `if`: perl prints `2|1!|`, HEAD prints `1|1!|`.
  - A read inside an arm and again after the merge: lli fails with `'%tmp_102' defined with type 'i1' but expected 'i64'`.
- **Impact:** Silent wrong answers, which the goal rules out (DIFFERS + LLI_FAIL must be 0). The corpus does not hit these shapes yet.
- **Suggested fix:** Refuse with a GAP when a field store sits under a branch and the field is read after the merge, and when a field read in an arm is reused after the merge. Model the guard on the `_has_branch_guarded_store` guard that Subscript already uses (Context.pm ~7246). Keep the refusal until field memory Phis are lowered.
- **Confidence:** High
- **Found by:** Spec Compliance (`claude-opus-5-5[1m]`)

### [I3] `a-stamp-question-is-not-a-class-question.t` fails: the list-return arm gates on `isa Chalk::IR::Value`

- **Confidence:** High

### [I4] The phase-block guard refuses `use Module VERSION`, which loaded before
- **File:** `lib/Chalk/IR/Serialize/JSON.pm:895-904`
- **Bug:** B::SoN emits a `Call VERSION` for `use Scalar::Util 1.0 ();`. The guard allows only `require`, `import` and `unimport`.
- **Impact:** A program that loaded at base is now refused. This contradicts 0caa2d02's claim that "A program with use statements loads as before". It is the same kind of slip 485f8e70 fixed for `no`.
- **Suggested fix:** Add `VERSION` to the allowed names (see I5 for the tighter shape check).
- **Confidence:** High
- **Found by:** Contract & Integration (`claude-opus-5-5[1m]`)

### [I5] The phase-block guard lets user-written import/require calls through, and their effects are dropped
- **File:** `lib/Chalk/IR/Serialize/JSON.pm:896-904`
- **Bug:** The guard checks only the bare Call name. It does not check that the call has the shape a `use` produces.
- **Impact:**
  - `package Foo; sub import { print "imported\n" } … BEGIN { Foo->import }`: perl prints `imported` then `main`, chalk prints only `main` (DIFFERS).
  - The same happens with `BEGIN { require "./setup.pl" }` when the file prints.
  - Base gave the same output, but this guard was added to refuse effectful phase blocks.
- **Suggested fix:**
  - Accept only a `require` of a Constant bareword module, plus `import`, `unimport` or `VERSION` on that same Constant.
  - Refuse a `require` of a path, and an `import` on a package defined in the program.
- **Confidence:** High
- **Found by:** Error Handling (`claude-opus-5-5[1m]`)

### [I6] The `$ENV` defined bit applies only when the operand is the EnvRead itself
- **File:** `lib/Chalk/Target/LLVM/Context.pm:4489-4495` (used at 4327, 4507)
- **Bug:** `_env_defined_bit` returns the bit only for a direct EnvRead operand.
- **Impact:**
  - `$ENV{U} // $ENV{U} // "z"` prints an empty string where perl prints `z`.
  - `$c ? $ENV{U} : "z"` under `defined` prints `d` where perl prints `u`.
  - Both were wrong at base too. The direct forms are now fixed, so a89f4e3b's claim is only partly met.
- **Suggested fix:** Pass the bit through DefinedOr, Ternary and Phi, or refuse with a GAP when the operand is derived from an EnvRead indirectly.
- **Confidence:** High
- **Found by:** Spec Compliance, Error Handling, Logic & Correctness (`claude-opus-5-5[1m]`)
